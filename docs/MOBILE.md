# GetMe native apps (Android and iOS)

Three store apps are built from the one web codebase with Capacitor:

| App | Target | App id | Who | Extra native capabilities |
| --- | --- | --- | --- | --- |
| GetMe | `customer` | `in.getme.app` | shoppers | push, camera, location |
| GetMe Partner | `partner` | `in.getme.partner` | delivery partners and community runners | **background location**, push, camera, haptics |
| GetMe Shops | `shop` | `in.getme.shops` | shop owners | push, camera |

The web app itself keeps working for everyone (PWA); the native shells add the permissions a browser cannot give, above all location with the screen off for partners.

## How the targets work

- `VITE_APP_TARGET=customer|partner|shop` at build time picks the title, icon, manifest and the start path. `pnpm --filter @getme/web build:targets` writes `apps/web/dist/customer`, `dist/partner`, `dist/shop`.
- `apps/mobile/<target>/capacitor.config.ts` is one Capacitor app per target (its own app id, name and `android/` and `ios/` folders), all pointing at the matching `apps/web/dist/<target>`.
- `apps/web/src/lib/native.ts` is the only place that touches Capacitor plugins. In a browser every helper is a no-op or falls back to the web API, so there is one code path for screens.

## One-time setup on a development machine

Requirements: Node 22, pnpm, Android Studio (SDK 34+, JDK 17), and for iOS a Mac with Xcode 15+ and CocoaPods.

```bash
pnpm install
pnpm --filter @getme/web build:targets
cd apps/mobile
pnpm add:android                      # android/ folders for customer, partner and shop (already in the repo; rerun only if deleted)
(cd customer && pnpm add:ios)         # Mac only, once per target
(cd partner && pnpm add:ios)
(cd shop && pnpm add:ios)
pnpm assets                           # icons and splash screens for all targets
pnpm sync                             # copies web builds and plugin config into the native projects
```

The Android projects live at `apps/mobile/<target>/android`; iOS projects are generated on a Mac at `apps/mobile/<target>/ios`.

### Point the shell at a server

`apps/mobile/capacitor.base.ts` (shared by the three configs) has `server.url` commented out. During development set it to your running web app (`http://192.168.1.20:5173` with `cleartext: true`, or an HTTPS tunnel) so the shell loads live code without rebuilding. For releases leave it unset: the built web files are bundled in the app and talk to the API at `VITE_API_URL`, so build the web targets with `VITE_API_URL=https://api.getme.example.in`.

## Partner app: background location

The partner build uses `@capacitor-community/background-geolocation` while a job or trip is active. It shows the required foreground notification on Android ("On a delivery") and uses the `location` background mode on iOS.

Android `AndroidManifest.xml` (generated by `cap sync`; verify):

```xml
<uses-permission android:name="android.permission.ACCESS_FINE_LOCATION" />
<uses-permission android:name="android.permission.ACCESS_COARSE_LOCATION" />
<uses-permission android:name="android.permission.ACCESS_BACKGROUND_LOCATION" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_LOCATION" />
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />
<uses-permission android:name="android.permission.CAMERA" />
```

iOS `Info.plist` keys: `NSLocationWhenInUseUsageDescription`, `NSLocationAlwaysAndWhenInUseUsageDescription` ("GetMe Partner shares your location with the customer only while you are on a delivery"), `NSCameraUsageDescription`, `NSPhotoLibraryUsageDescription`, and `UIBackgroundModes` → `location`, `remote-notification`.

Google Play requires a declaration for background location: the use case is "delivery partner sharing live position with the customer during an active delivery", with an in-app prompt that explains it before the system dialog (the partner app shows it on the first job).

## Push notifications

The API sends Web Push to browsers and FCM to native devices from the same `notify()` call, with SMS as the fallback.

1. Create a Firebase project; add three Android apps (the ids above) and three iOS apps. Download `google-services.json` into `apps/mobile/<target>/android/app/` and `GoogleService-Info.plist` into the iOS projects.
2. For iOS upload your APNs key to Firebase (Project settings → Cloud Messaging).
3. Create a service account (Project settings → Service accounts → Generate new private key) and set `FCM_SERVICE_ACCOUNT_JSON` on the API to the file path or the JSON itself.
4. The apps register on sign-in (`registerNativePush`) and store the token at `POST /api/push/native`. `GET /api/health` shows `nativePush: true` when the service account is loaded.

Tapping a notification opens the URL in its payload (for example `/partner/job`).

## Building releases

Android:

```bash
cd apps/mobile/partner
pnpm sync
pnpm open:android              # Android Studio → Build → Generate Signed Bundle (AAB)
```

Or from the command line: `cd apps/mobile/partner/android && ./gradlew bundleRelease` with your keystore in `app/build.gradle` signing config. Use a separate keystore per app or one upload key for all three.

iOS: `cd apps/mobile/partner && pnpm open:ios`, set the team and bundle id in Xcode, archive and upload with Transporter or Xcode Organizer.

## Updating the apps

Web-only changes (screens, copy, theme) do not need a store release when `server.url` points at your hosted web app. For bundled builds: `pnpm --filter @getme/web build:targets && pnpm --filter @getme/mobile sync`, then rebuild and upload.
